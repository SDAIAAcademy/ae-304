Questions over a warehouse

No page holds "how many students enrolled last semester"

  • The answer is computed from rows: a query over the enrolment warehouse
  • Retrieval of documents cannot find it, however good
  • The tempting shortcut: let the model write the SQL

Al-Nuha's warehouse

Five tables: colleges, programmes, students, terms, enrolments. 6,967 students and 162,600 enrolments, synthetic. Owned by Abdulrahman Al-Duwaish, institutional research.

The warehouse is DuckDB over CSV files in labs/data/warehouse. The students table is Restricted: it holds gender, nationality and status per student. Keep that in mind for the last step of the lab.

Lab 4.1, step 1

TABLE enrolments (student_id BIGINT, term_id VARCHAR, course_code VARCHAR,
  credit_hours BIGINT, status VARCHAR, letter VARCHAR, grade_points DOUBLE)

What the schema does not say. That a withdrawn enrolment does not make a student enrolled, that term ids are Gregorian, or that MIS was merged into IS.

The schema is the honest version of what most text-to-SQL demos send. Every business rule that is not in it is a planted trap: they are the warehouse's real-world equivalents, and the lab names them in step 4.

How to score SQL

Execution accuracy: run the query and compare the result with the reference

Not the text

Two different queries can both be right.

Not "it ran"

A query that runs can return a wrong number.

The result

Equal to the reference answer, within rounding for rates.

Benchmarks such as BIRD report execution accuracy for the same reason.

Each of the 20 questions has a reference SQL written by the institutional research lead and its answer. Sources: BIRD benchmark (see course sources).

12 of 20 free queries read the Restricted students table

"How many students were enrolled in the second semester of 2025/2026?" The model's query counts every student with an enrolment row in the term and returns 4,912. The reference returns 4,780. The query runs without error. What went wrong most likely?

A syntax error the database ignored
The model could not read the enrolments table
A missing filter: withdrawn enrolments were counted as enrolled
The model is too small for SQL
Why. The count is higher than the reference by students whose only enrolments were withdrawn: a business rule that lives in the institution, not in the schema.

Lab 4.2, step 2

Code turns the request into SQL over the governed views only

{"metric": "credit_hours",
 "filters": {"term": "2025-1",
             "college": "ENG"}}
SELECT SUM(credit_hours)
  FILTER (WHERE status <> 'withdrawn')
  AS value
FROM enrolment_facts
WHERE term IN ('2025-1')
  AND college IN ('ENG')

The compiled query from the lab's step 2, the same question as S09, which free SQL got wrong (13,092 instead of 12,270). The rule is in the metric definition, so the model cannot forget it.

Cost, latency and freshness

Three numbers decide whether Nibras can serve a whole university

Cost per question

Tokens in and out, times the price. The design sets the tokens.

Tail latency

The 95th percentile, by stage: one student in twenty waits that long.

Freshness

How long after a circular changes it becomes searchable.

These are the numbers the capstone README reports next to the quality metrics. Ask which one the vice-rector will ask about first. Usually cost; the students will notice latency; the registrar will notice freshness.

Freshness

A corrected circular: re-index everything, or only what changed

What goes wrong. The text is updated and its old vector stays. Dense search then ranks the page by what it used to say. Mark the vector stale and skip it until it is re-embedded.

Lab 4.3 steps 3 and 4. The embedding time is estimated from the measured 300-page time; the lexical times are measured. After the incremental update, a search for the new rule finds the page at once, and dense search skips that one page until its vector is rebuilt. The capstone's staleness tests should include a changed document.

Session 4

Diagnosing failures by component

  • Attribute a failure to parsing, retrieval, ranking or generation
  • Fix the weakest component and measure again
  • Explain why failures move down the ladder
04
Diagnosing failures

"The model is bad" is not a diagnosis

  • Students reported 20 wrong answers from Nibras
  • Each has a trace: the parsed text, the 50 candidates, the top 5 the model read, the answer
  • The question for each: which component lost the answer first?

Why it matters

A new model does not fix an empty parse. A new parser does not fix a prompt. Fix the component that failed, then measure again.

The traces are synthetic, written by prepare_data.py so that each failure is built to fail in a known component; the re-parse and the search in the lab are real. Ask the room how they diagnose failures today: usually by reading the answer, which is the last step of the pipeline.

The attribution ladder

Walk down the pipeline and stop at the first component that lost the answer

1 · Parsingare the needed words in the parsed text?
→
2 · Retrievalis the page among the 50 candidates?
→
3 · Rankingis it in the top 5 the model read?
→
4 · Generationdoes the answer contain the needed words?
Order matters. A page that was never parsed cannot be retrieved; blaming retrieval would send you to the wrong fix.

Compare the text after NFKC and normalisation, or presentation forms hide a match and every Arabic failure looks like parsing. That is the first bug the lab's step 2 catches.

Into the capstone

The defence asks you to explain one failure by component

  • Pick a failure from your own test set or your traces
  • Show where it stopped on the ladder, with the evidence for each step
  • Say what you changed, and the before and after counts
Takeaway. The method is cheap: four checks per failure, no model needed. Run it every time the error count moves.

The lab writes artifacts/D4_4/attribution.json. Point to the capstone rubric: "Agentic or structured-data component" and "Reproducibility" both reward a diagnosis that someone else can rerun.
