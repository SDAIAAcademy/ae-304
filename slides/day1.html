Judging only answers

A model can answer from memory with the page missing, or paraphrase a superseded rule fluently.

Judging retrieval

Was the page that answers it in the top 10, and how high? Cheap, repeatable, no model needed.

Ask the room which layer they would fix first if the answers were wrong. The honest answer is "I don't know yet", and that is the point of a retrieval test set. Day 4 closes the loop by attributing failures to parsing, retrieval, ranking or generation.

The bias. A new system that finds pages no pooled system found is scored as wrong on them. Add its top results to the pool before you compare.

Pooling is how TREC-style evaluations stay affordable. In the lab each pair judges 20 queries from supplied pools, then compares with the reference grades. The stretch asks for five new queries as test set v1.1: version the test set like code.

Three numbers, three questions

Recall, reciprocal rank and nDCG measure different failures

Recall at 10

Of the relevant pages, how many are in the top 10? The model cannot read what is not there.

Reciprocal rank

1 over the rank of the first relevant page. Does the answer come first?

nDCG at 10

Rewards grade 3 above grade 1 and high ranks above low ones, scaled 0 to 1.

dcg = sum((2**grade[p] - 1) / log2(rank + 1) for rank, p in enumerate(top10, 1))
ndcg = dcg / ideal_dcg   # the same sum over the best possible order

Write a toy ranking on the board: relevant pages at ranks 2 and 5 out of two relevant pages. Recall at 10 is 1, RR is 0.5. The lab checks your three functions on a toy ranking before it scores the baseline (the check prints 0.5, 0.5 and 0.574).

Lexical search

An inverted index maps each word to the pages that contain it

TermPages
withdrawArticle 25, Circular 2026-031, guide/withdrawal
postponeArticle 26, guide/postponement
semester924 of the 2,617 Public pages
  • A query looks up its words, not every page: fast at any size
  • Exact words only: "withdrawal" and "withdraw" are different keys unless you stem
  • Every database has one: SQLite FTS5, PostgreSQL full-text search, OpenSearch

Ask for the weakness before showing the bullets: what happens to a student who writes "drop a course"? The index has no idea that "drop" means "withdraw". Hold that thought for Session 3, dense retrieval.

How BM25 weighs words

BM25 rewards rare words and saturates repeated ones

Rarity

"postpone" in 9 pages weighs far more than "semester" in 924.

Saturation

The tenth "postpone" in a page adds little over the third.

Length

A match in a short page counts more than in a long one.

CREATE VIRTUAL TABLE idx USING fts5(id UNINDEXED, text);
SELECT id, bm25(idx) FROM idx
 WHERE idx MATCH '"withdraw" OR "course" OR "deadline"'
 ORDER BY bm25(idx) LIMIT 10;   -- lower is better in FTS5

No formula on the slide on purpose; the two parameters (k1 for saturation, b for length) are worth a sentence each if the room asks. Note the FTS5 quirk: bm25() returns more negative numbers for better matches. The lab's helper flips the sign.

What goes wrong. Students type fast on phones and skip the hamza; the regulation is typeset carefully. Raw matching punishes exactly the users you serve.

Ask an Arabic speaker in the room how they type "الأولى" on a phone. Then show the normaliser's output in the lab: it prints a normalised phrase so participants can see each rule work.

The fix

Normalise and lightly stem both the pages and the query

1 · Normaliseremove diacritics and tatweel; unify alif, ya, ta marbuta
→
2 · Light stemstrip ال, و, ب and common suffixes
→
3 · Indexthe analysed words, not the raw text

The classic bug

Normalising the pages but not the query, or the reverse: every match fails silently.

Light, not deep

A root-based stemmer merges words with different meanings. Light stemming removes affixes only.

Tools for production: CAMeL Tools and PyArabic both ship normalisers and morphological analysers. In the lab you write a dozen lines yourself so you know what each rule does; the stretch gives the title its own column and weight.

Dense retrieval

An embedding places texts with similar meaning close together

  • A model turns each page into 384 numbers; the query too
  • Search is a dot product of the query with every page
  • Multilingual models put an Arabic question near an English answer
  • No word has to match: "drop a course" can find "withdrawal"

The two models of Lab 1.3

multilingual-e5-small and paraphrase-multilingual-MiniLM-L12-v2: open weights, 384 dimensions, small enough for a laptop processor or a free Colab runtime.

Keep the maths light: cosine similarity on normalised vectors is the dot product. The labs read supplied vectors on a laptop (data/vectors/), made with these two models; in Colab the models load and embed the 300-page sample live. Nothing downloads a model on a participant's laptop unless they set AE304_MODELS=load.

Hybrid search

Lexical and dense search fail on different queries

BM25 finds

Course codes, circular numbers, article numbers, exact names: "CSC 301", "2025-118".

Dense finds

Paraphrases, everyday words, the other language: "drop a course", a question in English about an Arabic page.

The idea. Run both, then merge the two rankings into one. The question is how to merge two lists whose scores are on different scales.

Ask the room for a query each method would fail on. A code like "CLS 334" has no meaning for an embedding model; "how do I stop my studies for a term" has no word in common with the article.

What goes wrong. Add raw scores and BM25 decides everything. Normalise them and you add a weight to tune, and it moves with every corpus change.

From Lab 1.4 step 2, min-max normalised scores mixed with weight alpha. The weight that wins here is not a constant: it is a parameter you would have to re-tune whenever the corpus or the model changes.

Use ranks, not scores

Reciprocal rank fusion adds 1 / (60 + rank) from each list

def rrf(rankings, k=60):
    score = defaultdict(float)
    for ranking in rankings:
        for rank, page in enumerate(ranking, 1):
            score[page] += 1 / (k + rank)
    return sorted(score, key=score.get, reverse=True)

The second stage

A cross-encoder reads the query and each candidate together

1 · First stageBM25 and dense, fused: top 30 in milliseconds
→
2 · Reranka model scores each (query, page) pair: 30 model calls
→
3 · Top 5what the generator reads

Why it is better

It sees both texts at once, so it can judge whether the page answers this question.

Why it is slow

One forward pass per candidate, every query. Nothing can be computed ahead.

The lab uses mmarco-mMiniLMv2-L12-H384-v1, a multilingual cross-encoder with open weights. Its scores for the fused candidates are supplied (data/reference/rerank_scores.json), computed once on a laptop, so no participant downloads it; they cover 92% of the fused top 30.
