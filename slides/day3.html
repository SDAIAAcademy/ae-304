The description is the interface

A tool description tells the model when to call it, not only what it does

def keyword_search(query: str, k: int = 5) -> list[dict]:
    """Keyword search (BM25, Arabic normalised). Best for exact
    words: course codes such as "CSC 301", circular numbers such
    as "2025-118", article numbers and names. English or Arabic."""
  • The function's docstring becomes the tool's description in the schema the model sees
  • Examples of when to use it beat a list of features
  • The stretch writes a misleading description and watches the choices change

The schema is generated from the signature and the docstring by U.tool_schema, so the description cannot drift from the code. With a live model, the stretch is the most instructive five minutes of the day: swap the descriptions of keyword and vector search and rerun.

Call the model, run the tool it asks for, append the result, repeat

messages = [system, {"role": "user", "content": question}]

Search again from what you read

The iterative loop: search, read, decide the next search or answer

notes, asked = [], set()
while True:
    d = decide(question, notes)             # the model, or the stand-in
    if "answer" in d:
        return d["answer"]
    q = d["search"]
    if q in asked or len(notes) >= max_searches:
        return decide(question, notes, final=True)["answer"]
    asked.add(q)
    notes.append({"query": q, "top": hybrid_search(q, 3)})

Three stop rules: an answer, a search budget, and a repeated query, which means the decider is going round in circles. The final call forces an answer from the notes so far, which may be "I could not find it". That honest answer is better than a guess.

The fix

Offload: write the result to a file and return a stub

def offload(result, limit=1500):
    if count_tokens(result) <= limit:
        return result
    path = OUT / f"list_courses_{n}.txt"
    path.write_text(result)
    return json.dumps({"file": path.name,
        "lines": n_lines, "pages": n_pages,
        "preview": result[:200],
        "hint": "search it with grep_file"})

Nothing is lost

The full result is one tool call away.

A tool for the file

grep_file(file, pattern) returns the matching lines and their count.

The stub says what is in the file and how to search it. The grep tool only opens files in the offload folder; the lab checks that a path outside it is refused (the notebook tries "../../nuha.py" and gets an error).

Knowledge graphs

Some questions are about links between facts, not about any one page

  • "Which courses must I pass, directly or indirectly, before PHY 401?"
  • "How many courses list CSC 201 as a prerequisite?"
  • "Which study plans include DSC 223?"
The shape of the answer. A chain or a set gathered from many pages. Search finds pages one at a time; a graph stores the links themselves.

The three kinds are the question kinds of Lab 3.4 (all prerequisites, dependants, plans that include a course) plus "must I pass X before Y". Ask how many searches the first one needs: one per link in the chain, and you do not know the length in advance.

The same rule as Session 1: the docstring is the description. A tool that runs a fixed query is safer than letting a model write graph queries, for the same reason Day 4 prefers governed metrics to free SQL.

When a graph earns its place

Build a graph for the relationships users ask about, not for the whole corpus

Worth it

Prerequisite chains, which plan includes what, which circular amends which article: few kinds of link, asked often.

Not worth it

"What does the regulation say about appeals?": one passage answers it, and search finds it.

Takeaway. A graph is a structured index for one family of questions. Keep it small, typed, and checked against its sources.

Three things to keep

Tools need descriptions

Say when to call each one; log the choice, the calls and the tokens.

Iterate with stop rules

An answer, a budget, a repeated query. Compare with one search on accuracy and tokens.

Keep the context small

Offload large results to files; put relationships in a small graph.
